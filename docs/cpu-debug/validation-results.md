# CPU 修复验证结果

本文件记录实际执行结果，不将编译成功当成真实 BPF 验证。
全核模式为 8 个 CPU worker，竞争模式为 16 个，均运行 15 秒。
每轮探针约 32 秒：6 秒基线、15 秒负载、余下时间验证恢复。

## 自动验收

- 内核加载及进程退出码为 0。
- 热点 PID 匹配本轮 stress-ng 的真实子进程；嵌套 namespace 中 worker PID 为 4～11。
- 基线与尾部三个样本为 NORMAL，加压后 10 秒内出现异常。
- 热点样本有有效且大于零的 BPF 运行快照差值。
- 运行时间不超过窗口加读取不确定度，不做数值截断。
- 倒序计数、RingBuffer 丢失及 Map 写入失败为零。
- 最终脚本额外检查 BPF/proc 使用率偏差不超过 15 个百分点。

## 最终结论及范围

最终采集核心在两次双倍 worker 竞争、一次嵌套 namespace 与一次最终全核测试中，
共 56 个热点样本均有有效运行证据；倒序、RingBuffer 丢失和 Map 更新失败均为 0。
竞争模式中单个热点线程约 50%～80%，不能要求每个线程都是 100%。

最终全核验证：14 个热点样本，BPF 比例约 99.54%～99.99%，最大 BPF/proc 差异约 1.37 个百分点。
一秒左右窗口没有再出现完整 4.39 秒片段混入，也没有高占用热点的零/无效运行证据。

少量 wakeup_miss（部分轮次为 1）不等同于 RingBuffer 丢失，可能来自探针中途接入等缺失基线。
本轮没有据此声称它必须永远为零，也未将它从报告中隐藏。

## 无特权回归

CTest 共 3 项通过：cpu_analyzer、cpu_runtime_window、json_reporter。
覆盖：高占用/压力分别计数、恢复、4.39 秒旧事件不能覆盖 1 秒快照、
缺失快照显式无效、TID 复用、累计倒退、不可能的窗口总量、每线程读取时间以及事件时间归窗。

## 记录位置

每个场景的 .json 保存机器可读汇总，.txt 保存完整程序输出，-stress.txt 保存负载输出。
保留 contention 的失败与负时间戳原始记录，用于理解加严测试如何推翻“普通负载通过就已修复”的判断。

这些短时测试证明当前条件下现象不再复现，不等同于已完成 ARM64 或数小时稳定性认证。
